# 태깅 정확도 측정 하네스 + 검색 실패사례 하네스

"체감상 70%"가 아니라 실제 숫자(recall/precision)로 AI 태깅 정확도를 재기 위한 도구.
2026-09-14, YOLO COCO 매핑을 24→70개로 확장한 뒤 처음 만들었다.

## 구성
- `ground_truth.json` — 테스트 사진 파일명 → 사람이 직접 눈으로 본 정답 태그(`required`: 반드시
  붙어야 함, `accepted`: 붙어도 오답 취급 안 함). 새 사진을 추가할 때마다 여기에 한 줄 추가한다.
- `measure_tagging_accuracy.py` — Room DB(`gallery_ai.db`)를 열어 `ground_truth.json`과 비교해
  recall/precision/F1을 출력한다.

## 사용법(에뮬레이터 기준)

1. 에뮬레이터 부팅 + 최신 APK 설치
   ```
   $ADB devices
   $ADB install -r app/build/outputs/apk/debug/app-debug.apk
   ```

2. (필요하면) 새로 검증하고 싶은 개념의 테스트 사진을 추가한다. 이 프로젝트는 위키미디어
   커먼즈 검색 API로 자유 라이선스 사진을 받아왔다(`fetch_commons.py` 패턴 참고 — 검색어로
   커먼즈 파일을 찾아 썸네일 URL을 받아 다운로드). **반드시 Read 툴로 직접 열어서 내용을 눈으로
   확인한 뒤** `ground_truth.json`에 정답을 적을 것 — 검색어만 보고 정답을 추측하지 않는다.
   ```
   MSYS_NO_PATHCONV=1 $ADB push my_test_photo.jpg /sdcard/Pictures/my_test_photo.jpg
   MSYS_NO_PATHCONV=1 $ADB shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE \
       -d "file:///sdcard/Pictures/my_test_photo.jpg"
   ```

3. 앱을 태깅시킨다 — 이 앱은 **검색을 한 번 실행하면 아직 안 된 사진 전부**를 백그라운드로
   분석한다(`MainActivity.searchWithMobileClip`의 `pendingUris`가 검색어와 무관하게 전체 미분석
   사진을 돈다). 사전에 있는 아무 한글 단어(예: "강아지")로 검색 한 번만 실행하면 됨.
   - **함정: `adb shell input keyevent 66`(ENTER)은 이 EditText(imeOptions="actionSearch")에서
     안 먹힌다.** 반드시 소프트 키보드에 실제로 뜨는 돋보기 아이콘(검색 액션 키, 보통 키보드
     우측 하단)을 `input tap`으로 직접 눌러야 `performSearch()`가 실행된다 — 좌표는 매번
     `adb exec-out screencap`으로 캡처해서 실측할 것(해상도가 기기마다 다름).
   - 분석이 끝났는지는 `pm clear` 직후라면 `photo_album.taggingVersion`이 전부
     `TagRepository.TAGGING_VERSION`과 같아지는지로 확인한다(아래 4번 쿼리 참고).

4. Room DB를 pull한다(`.db`+`.db-wal`+`.db-shm` 세 개 다 — WAL에 최신 커밋이 있을 수 있음):
   ```
   PKG=com.example.galleryai1
   for ext in "" "-wal" "-shm"; do
     $ADB exec-out run-as $PKG cat "databases/gallery_ai.db$ext" > "gallery_ai.db$ext"
   done
   ```

5. MediaStore 파일명 매핑을 뽑는다(`ground_truth.json`이 파일명 기준이라 필요):
   ```
   $ADB shell content query --uri content://media/external/images/media \
       --projection _id:_display_name > media_ids.txt
   ```

6. 측정 실행:
   ```
   python measure_tagging_accuracy.py --db gallery_ai.db --media-ids media_ids.txt
   ```
   사진별 recall/precision과 전체 요약(recall/precision/F1)이 출력된다.

## 2026-09-14 첫 측정 결과 (기준선, YOLO 매핑 확장 직후)

YOLO COCO 매핑 24→70개 확장 직후, 신규 개념 10장(위키미디어 커먼즈에서 받은 트럭/백팩/침대/벤치/
소파/컵/냉장고/텔레비전/우산/와인잔) + 기존 회귀 확인용 5장(돌고래/강아지/기린/미어캣/새)으로 측정:

- **recall(필수 태그 재현율): 93.3% (14/15)** — 신규 10개 중 9개 정확히 태깅됨(유일한 실패:
  정교하게 조각된 사찰풍 벤치를 "소파"로 오인 — YOLO가 훈련된 전형적 공원 벤치와 생김새가 많이
  달라서 COCO bench 클래스로 못 잡힌 것으로 추정). 기존 동물 5장은 전부 그대로 정답 유지(회귀 없음).
- **precision(예측 태그 정밀도): 46.2% (24/52)** — recall은 크게 개선됐지만, CLIP 제로샷이 같이
  붙이는 상관없는 태그(예: 백팩 사진에 스키/스노보드/테니스라켓, TV 사진에 컴퓨터/발표/키보드)가
  여전히 많다.

## 2026-09-14 (이어서): YOLO-CLIP 상충 억제 로직 추가 — 첫 시도는 오히려 recall을 깨뜨림

"YOLO가 찾은 클래스는 CLIP의 경쟁 후보를 억제한다"는 아이디어(`TagRepository.suppressYoloCompetingClipTags`)를
넣고 같은 15장으로 재측정했더니 **recall이 93.3%→73.3%로 오히려 추락**했다. 원인: 특이한 구도의
트럭(화려하게 장식한 파키스탄 트럭)/백팩(등산스틱과 뒤엉킨 채 문 앞)/와인잔(포도밭 말뚝 위) 사진은
**YOLO 자신도 그 클래스를 놓쳤는데(신뢰도 미달) CLIP은 정확히 맞췄던** 경우라, "YOLO가 없다고
했으니 CLIP도 지운다"는 규칙이 정답까지 같이 지워버렸다. → **`yoloDetections`가 완전히 비어있으면
(이 사진에서 YOLO가 단 하나도 못 찾았으면) 아무 것도 억제하지 않는 가드를 추가**해서 수정 — YOLO가
그 사진에서 뭔가는 성공적으로 찾았을 때만("이 사진 자체엔 반응했다"는 근거가 있을 때만) 그 "없음"
판정을 다른 클래스에도 신뢰하도록 좁혔다.

**가드 추가 후 재측정(같은 15장)**:
- **recall 93.3%(14/15)로 복구** — 트럭/백팩/와인잔 전부 정답 유지.
- **precision 46.2%→48.0%(24/50)로 소폭 개선** — 냉장고 사진에서 YOLO가 실제로 냉장고를 찾았을 때
  CLIP이 같이 붙였던 "전자레인지" 오탐이 제거됨.
- 개선 폭이 작은 이유: 이번 표본의 노이즈 대부분(백팩 사진의 스키/스노보드/테니스라켓, TV 사진의
  컴퓨터/발표/키보드 등)은 **YOLO가 그 사진에서 아예 아무 것도 못 찾은 경우**라, 가드 때문에 이
  규칙 자체가 적용되지 않는다 — YOLO가 뭔가를 확실히 찾았을 때만 도움이 되는, 범위가 좁지만 안전한
  개선. 표본이 늘어나 "YOLO가 뭔가 찾은 사진에 CLIP이 같은 카테고리 오답을 얹는" 경우가 더 많아지면
  체감 효과도 커질 것.
- **교훈: 이런 종류의 로직 변경은 배포 전이 아니라 배포 직후 측정 하네스로 바로 재검증해야
  한다** — 처음 로직은 코드 리뷰만으론 그럴듯해 보였지만 실제 데이터로 돌려보니 정반대 효과가
  실측으로 드러났다. `tools/measure_tagging_accuracy.py`를 만들어둔 게 이 사고를 당일에 바로
  잡아낼 수 있었던 이유.

표본이 15장뿐이라 이 숫자 자체를 "전체 정확도"로 일반화하긴 이르다 — 사진 종류를 늘릴수록
더 신뢰할 수 있는 기준선이 된다. `ground_truth.json`에 계속 추가해나갈 것.

에뮬레이터 `/sdcard/Pictures`에 있던 나머지 사진 28장(단색 테스트 이미지 3장, 동물/자연 스톡사진

`ground_truth.json`에 그렇게 명시해둠). **파일명만 믿었으면 오답 정답지가 될 뻔한 경우가 많았다** —

프롬프트/사전 튜닝할 일이 있으면 참고할 것. 사용자 실제 여행 사진(KakaoTalk 9장, 배경이 복잡한
실사용 조건)에서도 recall은 전부 100%였지만 "테이블"/"식당"/"파티" 같은 분위기성 태그가 잔뜩
같이 붙어 precision을 깎아먹는 패턴이 뚜렷함 — YOLO-CLIP 상충 억제로는 못 잡는 종류(애초에 COCO에
없는 개념)라, 다음 precision 개선은 이 방향(장면/분위기 태그의 임계값·마진 재점검)을 볼 차례.

## 검색 실패사례 하네스 (`search_harness.py`)

"검색에 LLM을 넣어야 하나?"는 질문에서 시작 — 도입 전에 **실제로 지금 검색(Tier1 사전매칭 +
Tier2 CLIP 벡터검색)이 얼마나 실패하는지부터** 실제 코드/데이터로 확인하기 위해 만듦(2026-09-14).

### 구성
- `search_queries.json` — 테스트 질의 + 기대 매칭 사진 목록.
- `clip_embed.py` — Kotlin `ClipTokenizer`를 파이썬으로 재현한 토크나이저 + CLIP 임베딩 헬퍼
  (태깅 하네스와 공용).
- `search_harness.py` — `SearchSynonyms.kt`/`DateExpressionParser.kt`의 로직을 파이썬으로 이식해
  Tier1을 재현하고, 실제 DB의 사진 임베딩으로 Tier2까지 재현한다.

### 사용법
```
adb exec-out run-as com.example.galleryai1 cat databases/gallery_ai.db > gallery_ai.db
adb shell content query --uri content://media/external/images/media \
    --projection _id:_display_name > media_ids.txt
python search_harness.py --db gallery_ai.db --media-ids media_ids.txt --queries search_queries.json
```

### 발견한 것

**1. Tier1은 사전에 없는 단어가 하나라도 끼면 전체가 깨진다.** `expandGrouped()`는 사전에 없는
토큰을 "반드시 매칭돼야 하는 그룹"으로 취급하는데, 그 리터럴 문자열이 태그일 리 없어서 항상
실패한다. "메고"(백팩을 메고 있는), "없고"(부정), "여러"/"마리"(개수), "최근"(최상급) 같은 흔한
동사/조사 활용형이 전부 이 패턴에 걸려서, 핵심 명사(백팩/동물/꽃)가 전부 사전에 있어도 검색이
0건이 된다.

**2. (더 중요, 2026-09-14 이전엔 몰랐던 것) Tier2 안전망이 한글 문장에서 사실상 고장나 있었다.**
서로 의미가 전혀 다른 한글 질의 5개를 비교하면 코사인 유사도가 **0.93~0.98**(사실상 구분 불가) —
같은 내용을 영어로 비교하면 0.53~0.63으로 정상. CLIP 텍스트 인코더가 영어 전용 바이트레벨 BPE라
긴 한글 문장이 의미 없는 바이트 조각으로 쪼개지면서 전부 비슷한 "노이즈" 임베딩으로 수렴한 것.
그 결과 Tier2는 질의 내용과 무관하게 항상 같은 사진 4~5장(KakaoTalk 음식/인물 사진)만 상위로 뽑음.
**→ `orangutan photo`처럼 영어로 번역해서 넣으면 정답 사진이 1위로 튀어오르는 것을 확인**하고,
`TagRepository.vectorSearch()`에 `TranslationTagger.translateToEnglishBlocking()`을 연결하는
수정으로 이어짐 — Tier1 경로엔 이미 번역이 연결돼 있었는데 Tier2만 빠져 있었다. **에뮬레이터
실기기 검증 완료**: "오랑우탄 사진" 검색이 수정 전엔 완전히 무관한 사진들을 반환했다가, 수정
후(번역 모델 다운로드 완료 뒤 재검색) 정확히 오랑우탄 사진 1장만 반환함.

**3. 질의 파싱이 아니라 태깅 자체의 한계인 경우도 있다.** `"사람 백팩"`(동사 없이 명사만, Tier1
AND가 이론적으로는 통과해야 함)도 실패했는데, 원인은 파싱이 아니라 **그 사진이 애초에 "백팩"
태그를 못 받았기 때문**(작게 멘 배낭이라 CLIP 확신도 낮음)이었다. 이런 경우는 질의 이해를 아무리
개선해도(LLM을 넣어도) 못 고친다 — 태깅 쪽 recall 문제라서.

**4. 부수 발견 — "실내"/"실외" 제외 목록 추가(위 항목)의 부작용.** 이제 이 두 태그는 `tag_master`에
아예 없어서, "실내에 있는 침대 사진"처럼 "실내"를 포함한 복합 질의는 그 그룹이 영원히 매칭 안 되는
Tier1 그룹이 되어 무조건 Tier2로 밀려난다. precision 개선이 이런 복합질의 recall을 깎는 트레이드
오프가 있다는 것 — 당장 되돌릴 정도는 아니지만 인지해둘 것.

### 결론
**검색 LLM보다 번역 연결(공짜, 이미 있는 컴포넌트 재사용)이 훨씬 비용 대비 효과가 컸다.** 남은
구조적 한계(부정문/개수 세기/최상급-정렬)는 사전+임베딩 아키텍처로는 원천적으로 안 되는 것들이라,
정말 필요해지면 그때 LLM을 다시 검토할 것 — 이번 조사로 "무엇을" 위해 LLM이 필요한지가 훨씬
명확해졌다(복합 문장 이해가 아니라 부정/개수/정렬 같은 논리 연산).

### 2차 배치(`search_queries_batch2.json`) — 번역 fix 배포 후 추가 검증

fix 적용 후 AND 로직 성공 사례, 새 COCO 개념의 할루시네이션 여부, 번역이 실제로 얼마나 도움되는지를
더 넓게 확인. 7개 전부 정상/개선:

- **"음식과 그릇이 있는 사진" → 4/4 정확 일치.** 실제로 두 태그가 같이 붙은 사진만 정확히 AND로
  걸러짐 — Tier1 다중 그룹 로직이 잘 동작함을 재확인.
- **"군인이 밥 먹는 사진" → 에뮬레이터 실기기로 확인, 성공.** "군인"이 사전에 없어 Tier1은 실패하지만
  번역("a soldier eating rice")한 Tier2가 정답 사진(군복 입은 인물이 밥 먹는 사진)을 유사도
  **0.301**로 정확히 찾음. **2026-09-05 세션에서 "AI 인식 한계로 수용"했던 "군복 검색 약함" 문제가
  이번 번역 fix로 부분적으로 개선된 사례** — 다만 "군복" 자체를 직접 검색하는 게 아니라 "군인이 밥
  먹는"처럼 맥락을 풀어 쓴 문장에서만 Tier2로 걸린다는 점은 인지해둘 것.
- **"커피잔 사진" → Tier1만으로 이미 성공.** "커피잔"이 사전 표제어는 아니지만, `matchDictionaryTerms`가
  부분 문자열 포함(`"커피" in "커피잔"`)까지 잡아내는 기존 설계 덕분에 별도 수정 없이 이미 됨.
- **"고양이 사진"/"얼룩말 사진"(둘 다 실제로 없는 사진) → 정확히 0건.** 새로 추가한 COCO 개념
  (얼룩말)이 비슷하게 생긴 다른 사진(기린)에 오탐을 내지 않는 것까지 확인(최고 유사도 0.176,
  임계값 0.18 미달) — 46개 확장이 할루시네이션을 늘리지 않았음을 보여주는 근거.
- **"밤에 불꽃놀이 하는 사진" → Tier1만으로 성공.** "하는"이 조사 제거 규칙("는")에 걸려 한 글자
  "하"로 줄어들고, 그 한 글자가 사전에 없어 자동으로 걸러지는 규칙(어간 조각 필터)에 우연히
  맞아떨어져 문장 전체가 깨지지 않음 — "메고"/"없고"처럼 조사 제거 후에도 2글자 이상 남는 동사는
  여전히 Tier1을 깨뜨린다는 점과 대비되는, 규칙 기반 파싱의 "운이 좋으면 통과" 특성을 보여주는 사례.
